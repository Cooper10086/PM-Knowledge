# PM 方法论工具箱：从"讲清楚"到"说得懂"

> 15 分钟团队内部分享 · 能力域 A（表达与文档规范）+ 能力域 B（协作与系统设计语言） 基于《产品经理学习资料》1-8 模块，案例均来自 Copy Trading 真实项目

---

# 一、能力域 A：表达与文档规范（模块 1、2、3）

目的：让图来辅助需求理解，让研发团队可快速的对齐需求框架与目的。顺序是先讲清"业务逻辑"（五张图），再讲清"文档结构"（PRD 六段式），最后是界面细节。

### 工具① 五张图：先讲清业务的"灵魂"

| 图       | 作用                        |
| :------ | :------------------------ |
| ① 核心体验图 | 业务主线 + 转化率"北极星"，对齐团队最底层共识 |
| ② 产品模块图 | 顶层系统架构，划清团队与考核边界          |
| ③ 产品功能树 | 穷尽功能细节，明确技术开发边界           |
| ④ 页面关系图 | 与功能树互相校验，防止"孤岛页面"         |
| ⑤ 交互图   | 界面元素与交互细节                 |

**Case RTC-185「复制订单来源明细展示」**

这是一个 Story 级需求，不是从 0 到 1 的大版本，所以我们没有五张图全画，而是重点做了 
**④ 页面关系图**——分别画出 Provider 端和 Follower 端的页面流转图。这2 张图可以帮忙研发理清楚页面的关系结构与页面中存在主要功能/逻辑点。

	- [[01 模块 产品经理必学的五张图#1. 带单端 (Provider-Side) 页面流转图]]

 2. Follower 页面流转图
	 - 跟单端优化的核心是让 Follower 清晰地核对自己的跟单行为，并理解每一笔订单的收益归因。

### 工具② PRD 六段式结构 + 写作心法

**PRD 六段式**（模块 3）：版本说明 → 背景与目标 → 故事介绍 → 概要设计 → 详细设计 → 交付设计

**对照 RTC-185 实际怎么写的**：

- **背景与目标**：Provider 需要清晰看到自己发出的信号订单被哪些 Follower 复制、费用计算详情和佣金明细；Follower 需要清晰核对自己的跟单行为，知道都复制了哪些订单及理解每笔订单的收益归因——这就是这个需求"为什么要做"。
- **故事介绍**：拆成了 4 个 Story——Provider 订单端监控、Provider 费用端对账、Follower 订单端追溯、Follower 费用端流向，一件事一行字，团队一看就懂要做什么。
	1. Follower 打开“复制订单”持仓或历史列表，发现某笔黄金订单显示为红色状态字样“已跳过”。
	2. Follower 点击该“已跳过”标签，界面弹出交互提示框。
	3. 提示框中以多语言展示用户可理解的具体跳过原因（如“您的可用资金不足，无法复制开仓”）。
	4. Follower 点击“知道了”关闭弹窗，知晓原委，未发起客诉。
	5. Provider 打开“信号源订单”列表，查看持仓订单的被复制概况。
	6. Provider 在列表中发现有 3 笔订单显示“已跳过”。
	7. Provider 点击“已跳过”标签，弹窗显示“由于跟随者跟单策略限制，已跳过 3 笔复制”。
- **概要设计**：上面那2张页面关系图 + 一张"复制订单状态与跳过原因逻辑映射表"（把 Brokeree 返回的 SkipByInvalidFunds 这类后端 Key，映射成中英文提示文案）[[01 模块 产品经理必学的五张图#3. 复制订单状态与“跳过原因”逻辑映射表]]。
- **详细设计**：针对每个跳过原因逐一定义触发逻辑和展示文案，避免研发对着后端字段自己瞎猜怎么显示。
- **交付设计**：提前定义了埋点方案（如 `skip_reason_pop_view` 事件，携带 order_id、skip_reason_key 等参数）和报表设计（数据门户里的"复制失败分析看板"），而不是等上线后才发现这个数据没法统计。

**写作心法**（模块 2，挑三条最关键，都能在 RTC-185 上找到对应）：

1. **PRD 提前评审机制**——RTC-185 涉及 Brokeree 接口高频交互，PM 提前 1-2 天单独拉了 Dev-BE 负责人做预评审会，把 positions 和 Deals 的订单号映射规则确认清楚，避免正式评审会上卡在技术细节。
2. **字不如表，表不如图**——"跳过原因"这类复杂的状态逻辑，如果用大段文字描述，研发和测试很难对齐；改成一张 Key→中英文文案→触发逻辑的映射表，一眼就能查。
3. **大声朗读法**——这条更适合日常自查：写完一段背景或规则描述，念一遍，绕口的地方基本都是逻辑没理清楚，不是文笔问题。

# 二、能力域 B：协作与系统设计语言（模块 4、5、6、8）

**共同逻辑**：不用变成架构师/数据工程师，但要会问对问题、讲对"共同语言"。这四个模块本质都是"翻译"——把业务目标翻译成研发能排期的任务，把运营诉求翻译成数据团队能实现的规则。

### 工具① 需求金字塔与 Sprint 容量语言（模块 4）

公司目标 Goal → 大版本 Version → 用户故事 Story → 系统功能 Feature → 原子任务 Task

容量公式：**Capacity = 研发人数 × 冲刺天数**，预留 15%-20% 缓冲应对线上 Bug 与技术债。这是我们跟研发对齐"这个需求这个迭代做不做得完"的通用语言，也是接下来 Follower 流失预警案例落地时要用到的拆分方式。

### 工具② CRM 决策框架（模块 5）

标签 Tagging（单维度，越简单越好）→ 分群 Grouping（固定/周期/实时三种）→ 动作 Action（工具+优惠策略+触达渠道）→ 执行计划 Schedule（绑定分群+动作，设 Slot 优先级）

**防打扰设计**：当用户同时命中多个执行计划时，用 Slot 优先级排队（互斥模式），而不是让所有计划同时轰炸同一个用户。

### 工具③ 跟数据团队对话的两个提问（模块 6、8）

- **"这个数据是实时的，还是隔天更新的？"**——决定了能不能做"实时干预"（模块6：实时分群 vs 周期分群），也决定了这个功能该报周期跑批还是实时链路。
- **"这个指标口径谁定义？会不会跟别的报表对不上？"**——对应模块8"同义不同名/同名不同义"和数据质量六维度，上线前锁定口径，比上线后对账省十倍力气。

### 案例：Follower 流失预警 CRM 方案（PM 视角设计）

套用模块 5 的框架[[05 模块 从 0 到 1 设计 CRM 产品#实践产出]]，但动作要按交易平台的业务特性改造——不能照抄电商发券：

- **标签**：最近跟单天数 / 累计跟单笔数 / 近 7 天跳单率 / 账户净值区间
- **分群**：跳单率高（对功能失望）｜30 天未跟单（沉默流失）｜净值下降（资金枯竭风险）——三类风险不同，动作不能一样
- **动作**：跳单率高 → 推送"复制规则设置指引"；沉默流失 → 唤醒 Push + 新 Provider 推荐；净值下降 → 风险提示（不发券，因为交易平台现金激励有合规风险）
- **执行计划**：同时命中"跳单率高"+"沉默流失"时走互斥模式，优先处理跳单率高
- **落到 Story**（呼应工具①的需求金字塔）："作为运营，我希望识别高流失风险 Follower 并及时干预，以降低月流失率"——可以直接进 Sprint 排期，不需要先写一份大 PRD

# 三、总结与行动

**关键收获**：

1. 五张图 / PRD 结构的价值在"自洽校验"，不是走流程，也不是每次都要全套画满
2. 协作与数据语言的价值在"翻译"——让业务诉求变成研发能排期、数据团队能实现的东西

**下一步行动**：

1. 把 能力域 A、能力域 B 定制成我们可复用的 Agent 来辅助我们工作，目的是把重复性的内容交给机器，创造性的我们来负责同时可让 AI 校验方案的风险与弊端。
2. 把 Follower 流失预警方案作为下季度可立项的具体需求（我认为想法是好的，但具体要与业务方沟通来决定，一切以提高数据为准则）
